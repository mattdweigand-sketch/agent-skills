# Teach the simplest useful explanation

Read before outlining and during final review. This file owns teaching simplicity. `writing.md` owns the selected writing methods. Simplicity does not mean omitting a condition that changes the answer.

## The retell test

The main path passes when a curious 10-year-old could explain it back after one read. This tests understanding, not only short words. Three rules make it pass.

1. **Simple words.** Use everyday words first. Use the real technical terms the topic needs, such as API, app, or code. Show the example before each term, then define it in one plain sentence at first use. Aim for about 12 words per sentence in the main path.
2. **No skipped steps.** Each idea builds only on what came before. If the reader would have to guess a step, add it.
3. **Full truth.** Simplify the words, never the facts. Keep any condition, limit, or uncertainty that changes the answer, said plainly.

The main path is everything visible without opening optional sections. Put field names, code, request formats, extra numbers, limits, model names, and pricing in optional sections by default. Bring one into the main path only when the answer depends on it, and then explain it in plain words.

## The idea budget

Simple words are not enough if the main path holds too many ideas. Keep the main path inside this budget.

- **One main idea.** Name the single idea the reader must leave with. Cut or move anything that does not serve it.
- **About 250 words.** Count all main-path prose. Move the rest to optional sections.
- **One interactive part.** Use the one that shows the main idea. Put other comparisons in optional sections or cut them.
- **Only the terms the idea needs.** Each technical term must earn its place and get a plain definition.

## Name the topic, then tell a story

The top of the page names the topic and answers it in one plain sentence. For example, the title is "What [the topic] does" and the line below says what it does. A reader must know the subject before the story starts.

Then tell one short, concrete story about people and everyday things. Bring in the technology inside the story, with its real name and a plain definition. Keep the same story through the whole lesson. Put general rules and categories after the story, or in optional sections.

Choose the example that best shows the main idea for this topic and user. Look at where the topic is really used, such as a sales team, a support desk, a doctor's office, or a library. Do not default to the same example for every lesson. Reuse an example only when it is the best fit for the topic.

## Build the explanation

- Answer the user's actual question in one or two plain sentences at the top, under a title that names the topic. Do not begin with a glossary, product catalog, or history unless that is the question.
- Keep the main path to the ideas needed to understand that answer. Introduce one idea at a time, with prerequisites before dependent ideas.
- Use everyday words where possible. Define an unfamiliar term before relying on it. Do not explain one unknown term with several more unknown terms.
- Show a concrete case before adding abstractions. Carry the same example through the lesson so the reader does not have to learn a new situation for every distinction.
- Make the example show why the distinction matters. A changed condition, missing fact, or different action should change the result. Merely labeling components is not enough.
- State each section's conclusion directly. Explain the connection between facts instead of expecting the reader to infer it from a diagram.
- Keep optional context, code, parameters, pricing, and edge cases in expandable sections unless they are central to the question. Keep essential caveats beside the claims they qualify.
- Prefer literal examples to analogies. Label invented examples and preserve the source's uncertainty.
- Use real numbers from sources. If none fit, show no numbers. Never show made-up scores, prices, or outputs that look like real results.
- End with the answer the reader should now understand, and its practical consequence. Do not end with a list of newly introduced concepts.

## Review for simplicity

Read the main path without opening optional sections. Apply the retell test first.

1. Could a curious 10-year-old retell the main path after one read? If not, find the hard word, the skipped step, or the extra idea.
2. Does the top name the topic? Does the main path stay inside the idea budget and use the best example for this topic?
3. Does the opening answer the question rather than merely name the topic?
4. Does each idea build on something already explained?
5. Can a beginner follow the wording without looking up an undefined term?
6. Does the example show a meaningful consequence?
7. Do the section conclusions connect into one clear explanation?
8. Can any detail move out of the main path without losing the answer or an essential qualification?

If a check fails, fix the sequence, example, or missing explanation first. Shorter sentences, fewer words, attractive graphics, a low reading grade, and a passing language checker do not by themselves prove understanding.
