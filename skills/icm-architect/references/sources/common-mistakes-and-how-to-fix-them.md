**3.3 Common Mistakes and How to Fix Them**

## Diagnose one result at a time

A folder system should make your work easier to inspect and repeat. When it feels heavy, start with the task that failed. These are seven common places to look.

## Use the same method with your tool

The original examples use Claude and `CLAUDE.md`. With Codex, use `AGENTS.md` for project instructions. With ordinary chat, paste or attach the instructions and the specific source material for that task, then save the result yourself. A `CONTEXT.md` filename alone does not guarantee that its contents were read. ## 1. The entry file contains everything

Keep the map short enough to scan. Put detailed project facts, examples, and procedures in named files. Route a task to the relevant files instead of repeating all of them in the entry file.

## 2. The routing is implicit

Write a simple rule: “For a client follow-up, read `CONTEXT.md` and inputs/`meeting-notes.md`; write to drafts/.” Ask which files were used, then check the result.

## 3. The folder tree is bigger than the work

Start with one job and the few folders it needs. Split a workspace when different tasks need different context, permissions, or review. A folder count is a guide, not a correctness rule.

## 4. The instructions describe a personality, not a task

Audience, source facts, examples, output shape, and review criteria help you evaluate a result. A role such as “editor” can be useful, but it cannot supply missing project facts.

## 5. The context has gone stale

When a decision changes, update its source file. Date changing information, remove superseded directions, and keep the reason for important decisions.

## 6. Everything is in one undifferentiated pile

Group files by the work they support. Distinguish source material, working drafts, and reviewed outputs. Use filenames a teammate could understand.

## 7. The system is built before the first useful result

Run one small task before adding skills, automations, or more folders. Let a real failure or repeated need tell you what to change next.

## A repair you can test

*Fictional example:* a follow-up draft says “We will send the proposal Friday,” but the notes only say “Timing to confirm.”

- Find the source sentence. Keep its uncertainty.
- Add the rule: “Do not turn a suggestion into an approved commitment. Put missing owners and dates under Questions.”
- Rerun the same request. Check whether the draft now says the date is unconfirmed.
- Keep the change if it improves the result. Check another example before treating it as a reusable rule.
